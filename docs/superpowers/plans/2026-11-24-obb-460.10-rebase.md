## 6. `.rsbpatch` 容器侦察结论（决定 P0 的可行性与成本）

已确认的字段（两个补丁都成立；**2026-11-24 20:5x 已按二进制解析修正**，旧的「条目数 / 每段标记」说法作废）：

| 偏移 | 类型 | 补丁1 值 | 补丁2 值 | 含义 |
| --- | --- | --- | --- | --- |
| +0 | char[4] | `PBSR` | `PBSR` | magic |
| +4 | u32 LE | 1 | 1 | 容器版本 |
| +8 | u32 LE | 2 | 2 | 类型/算法号 |
| +12 | u64 LE | 2,095,579,136 | 2,096,463,872 | **源文件字节数**（补丁1 恰好等于我们 OBB） |
| +20 | u32 LE | 163 | 427,125 | **info-section 补丁流长度**（不是「条目数」） |
| +24 | 16 B | `37ac0818…8ed6` | `5f938695…66d9` | **源 OBB 前 `HEADER_SIZE` 字节的 MD5**（实测对上） |
| +40 | u32 LE | 4310 | 4313 | **报文条数 = 目标 OBB 的 subgroup 条数** |
| +44 | u32 LE | 1 | 1 | 标志位（实测恒 1） |
| +48 | 变长 | `d6 c3 c4 53 00 01 …` | 同 | info-section 的 VCDIFF 流，长度 = `@20` |

正文统计（旧结论，仅作背景）：补丁1 有 99 处 zlib 头（`78 01/9c/da`）但**逐个解压全部失败**（随机字节巧合，不是压缩流）；
补丁2 有 432 处 zlib + 4 处 zstd + 2 处 gzip；另有 1 处 ASCII `1bsr`（补丁2 offset 73，正是 OBB 容器的 magic）。

核心库 `libczProject.so`（460.11）里的实现线索（字符串）：
`rsbpatch truncated: packet info incomplete` / `cannot map packet ` / `failed to read target window length` /
`rsbpatch version not supported` / `rsbpatch package info unknown_1 check failed` /
`Diff: instruction stream ended early` / `rsbpatch check failed: before rsb info-section hash does not match patch` /
`Info-section VCDiff decode failed: ` / `[%u/%u] restored: %u` / `rsbpatch truncated: info-section patch incomplete`。

→ 结论：**自定义容器 + VCDIFF(xdelta) 指令流**，info-section 与数据段是两条独立补丁流，
   并且带「打补丁前 OBB 的 info-section 哈希」校验（这解释了为什么必须从**原版 460.1** 起打，
   任何被我们改过的 OBB 都会在第一道校验上失败）。

### 6.2 报文骨架（已破译，两条补丁都闭合）

```
文件 = 头 48 B + info 流(@20 字节) + 报文[条数=@40]
报文 = 描述符 152 B + payload(payloadLen 字节)
描述符:
  +0    u32  type         0 = 该 subgroup 未变（payloadLen 恒 0，直接拷贝源字节）
                           1 = 有 VCDIFF payload，需要解码
  +4    u32  payloadLen
  +8    char[128] name     NUL 填充，实测 "PACKAGES" / "__MANIFESTGROUP__" / "EffectElementReactionGroup_1536"
  +136  u8[16] beforeHash  源 subgroup 内容的 MD5（新建 subgroup 为空内容哈希 d41d8cd98f00b204e9800998ecf8427e）
打补丁:
  1) newHeader = vcdiff(source = src[0:HEADER_SIZE], patch = f[48 : 48+@20])
  2) 逐报文: type==0 → 拷源 subgroup 字节; type==1 → vcdiff(source=源 subgroup 字节, patch=payload)
  3) 按新 header 的 subgroup 表重排写出
```

实测闭合（`next = pos + 152 + payloadLen`）：

| 补丁 | 报文数 | 走完末位 | 文件大小 | 差 |
| --- | --- | --- | --- | --- |
| 460.1→460.2 | 4310 | 2,686,247 | 2,686,247 | 0 |
| 460.2→460.9 | 4313 | 9,767,076 | 9,767,076 | 0 |

### 6.3 payload 层：VCDIFF 方言（2026-11-24 20:40 实测）

> 结论先说：payload 是 **VCDIFF 家族但不是 RFC3284 原文**，xdelta3 直接解不了；容器层已闭合，剩下的是「指令流语义」。

#### 证据链

1. **社区确认方言来源**：PopStudio issue #21 明确「RSB Patch 用 vcdiff」（<https://github.com/PopGameTool/PopStudio/issues/21>）。
2. **官方核心库自己带实现**：`libczProject.so`(460.11) 内含 `rsbpatch version not supported`、`rsbpatch truncated: packet info incomplete`、`Info-section VCDiff decode failed: `、`Diff: instruction stream ended early`、`cannot map packet ` 等字面量；Java 侧 `Java_com_inject_HookSelectorActivity_startRsbPatchDecode` / `isRsbPatchDecodeSuccess` 是入口。
3. **xdelta3 3.2.2 实测（`work\_vcd4.py`）**：同一份 163 B info 流，
   - 原样 → `VCDIFF input version > 0 is not supported`；
   - 第 4 字节 `0x53` 改成 `0x00` → 解析到窗口但 `address underflow`；
   - `drop5` / `drop6` / 另拼标准头 → `unrecognized window indicator bits`。
   → 头 5 字节（magic4 + flags）与 RFC3284 的 `magic3 + version + hdr_indicator` 不同，字段顺序也不同。
4. **流头布局（`FUN_002c011c`）**：`d6 c3 c4 53` + `flags`，`flags` 的 bit0/bit1 是开关；游标从 **第 6 字节** 开始。`param_3[3] == 0` 也接受（两种 magic 变体）。
5. **指令形态（`FUN_002c0fc8`，一次一条）**：`mode = op & 3`；varint 为 **MSB-first base-128**；
   - mode 1 = 从源缓冲拷贝（`src + off`，边界 = 源长），mode 2 = 从已产出输出拷贝（`out + off`，边界 = 输出长），两者都读 **两个 varint**（长度、偏移）；
   - mode 0 = ADD 窗口：再读一个 varint 作为「子块字节数」，随后读 `(flags & 7) == 0` 的子操作码，再连读 **三个 varint** 得到 `data | inst | addr` 三段长度（三段总长必须 ≤ 子块字节数）——这就是一个 VCDIFF 窗口的三段区；
   - 驱动侧先以 `param_9 = 0` 跑，失败且 `(*op & 3) == 0` 时以 `param_9 = 1` 重试（ADD 有「长度在 opcode 高位 / 长度是显式 varint」两种读法）。
6. **卡点（如实登记）**：info 流前 6 字节之后是 `01 | 82 a3 80 00 | 00 | 0c | c0 80 00 00 00 …`。按上述规则第 1 条指令 mode1 读 (长度 4,767,744, 偏移 0) —— 正好整段旧头，可信；但接着 `0x0c` 走 mode 0 时读出的「子块字节数」是 **1,048,576**，远超 158 B 的流。⇒ 要么 `0x0c` 不是 opcode，要么 mode 0 的第一个 varint 归属不同。**这是唯一未闭合的点。**

#### 验收 oracle（不需要先打出整个 460.2）

补丁2 的 `@24` = `5f938695079f4a2812e0770ac261e066` = **460.2 头部区 MD5**。补丁1 的 163 B info 流解出来后 `md5(结果)` 必须等于它；结果长度应在 4,767,7xx 附近。

#### 三条并行路线

| 路线 | 做法 | 成本 | 风险 |
| --- | --- | --- | --- |
| A1 手工复刻（patcher，进行中） | 按 `FUN_002c0fc8` 伪代码把字段表定死，用 oracle 迭代 | 2–4 h | 伪代码类型传播不完整，读错字段顺序 |

### 6.4 装配层：目标 OBB 怎么拼出来（2026-11-24 21:05 实测）

实测 460.1（探针 `work\_sgtab.py`）：`header_size=4,767,744`、`subgroups=4310`、表在 `3,189,912`、条目 204 B；
**所有 (offset,size) 都是绝对文件坐标**，且：

- 第一行 `ALWAYSLOADED_1536` 的 offset **恰好等于** `header_size`；最后一行 `FishesGroup_Common` 结束 **恰好等于** 文件大小；
- `gaps=0`、`overlaps=0`、`trailing=0`、`zero-size rows=0`，且**表顺序就是 offset 顺序**。

→ 装配算法（不依赖任何猜测）：

1. 用 info-section 解出的 **新头**（长度仍是 `HEADER_SIZE`，两条补丁的窗口和都等于 `0x48C000`）作为目标头；
2. 按新头的 subgroup 表顺序逐条产出 blob：`type==0` 直接从**源 OBB 同下标**的 `(offset,size)` 拷字节；
   `type==1` 用 VCDIFF 结果；
3. 从 `header_size` 开始累加长度写文件，**然后校验**每一行「累加得到的 offset == 头里声明的 offset」，
   再校验「末尾 == 头里最后一行 offset+size」。任一处不等就**报错退出**，不许静默修正
   （静默修正会把「解码错了」伪装成「解码对了」）。
4. 验收：`md5(file)` 必须等于 manifest 的 460.2 / 460.9 值。

推论（对工时有用的两条）：未变报文是纯 memcpy，不需要理解 pgsr 内部；`PACKAGES` 变大 2 MB 只会挪动它之后所有行的 offset，
这是**头里的 offset** 决定的，拼接顺序不受影响。
