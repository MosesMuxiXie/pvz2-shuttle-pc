三条可直接引用的样例（`rewards[]` 里搜 id 即可）：

```
loot:Silver1:default   coin  10   [10,30]   period 2  kills   pkg_0234...:LootTable/DefaultLootTable.Entries[0]
loot:EgyptKey1:any     key   1    [1,1]     world egypt, EnabledAfter egypt3
loot:SunLarge1:whack   sun   75   [75,75]   period 0.5 seconds（打僵尸小游戏按时间而非击杀）
```

**读法要点（三条，都会影响引擎行为）**

1. `Period` 的单位是**击杀数**，不是秒。唯一的例外是 `whack` 那两条：0.3 / 0.5 不可能表示击数，本表因此写 `periodUnit="seconds"`——这是**推断**，不是字段声明。
2. 四条 key 掉落**没有 `LevelLootKey`**，所以不属于 `default`/`danger` 子集：它们在**任何**玩该世界的关卡里都可能掉，由 `World` 字段限定世界、`EnabledAfter=egypt3` 限定进度。这一点容易被误读成「钥匙只在特定关掉」。
3. 同一个 `UniqueId` 会跨 `LootConfig` 复用（`Silver1` 同时属于 `default` 与 `danger`），所以本表的 id 形如 `loot:<UniqueId>:<LootKey>`——**不要用 UniqueId 当主键**。

## §3 通关午餐盒（R03 / R04）——**部分可行**

`pkg_2079_PresentTable.json` 只有 **8 张表**（4 个世界 × normal/shiny），`Entries` 合计 36 条：

| 表 | 变体 | 条目 | 实际生效 |
|---|---|---|---|
| `egypt_normal_01` | normal | 1 | `coinpack_medium` weight 50 → **100 金币** |
| `egypt_shiny_01` | shiny | 8 | `coinpack_medium` weight 50 → 100 金币；另 7 条（5 powerup / bacon / sprout）weight 全 **0** → 关闭 |
| `pirate_*` / `cowboy_*` / `future_*` | normal+shiny | 同上 | 同上 |

- `PresentTypeCoin.CoinValue` 是**字符串**（`"10"/"100"/"1000"`），直接当数字用会得到 0——本模块统一走 `number()` 转。`coinpack_small=10`、`coinpack_large=1000` 定义了但没有任何 present 表引用它们。
- **shiny 的 7 条额外奖励权重全是 0**，所以「通关拿到的东西」在数据上 normal 与 shiny 完全一样（都是 100 金币）。什么时候用 shiny 列，数据里没有字段说明 → 见 `unknowns[]`。
- **13 张表是悬空引用**：`lostcity/dark/eighties/beach/heian/kongfu` 的 normal+shiny 表名在全库 2117 个文件里**0 定义**，却共有 **68 个关卡引用**。其中 `heian_normal_01` 既被 2 关当 normal 引用、又被 1 关当 shiny 引用，而这个表本身不存在。
- 反向的宽松读法也有 11 处：10 个关卡把 `ShinyPresentTable` 填成了 `egypt_normal_01`、1 关填成 `heian_normal_01`——数据里就允许 shiny 列指向 normal 表。

## §5 僵尸掉落与拾取物（R05）

- 拾取物实际值（`pkg_0010`）：`coin_silver` **10**、`coin_gold` **100**、`coin_gold_fake` 100、`coin_treasure_chest` **10000**；`gem_diamond` **2**；`sun_small` 5 / `sun_medium` 25 / `sun_large` 75 / `sun` 50；`moneybag` 30 枚银币、`big_moneybag` 200；10 个 `worldkey_*`（beach/cowboy/dark/dino/eighties/future/iceage/lostcity/modern/pirate，**没有 worldkey_egypt**）。
- **`LootTable.Type` → 拾取物之间没有映射表**。`SilverCoin/GoldCoin/Gem/SmallSun/LargeSun` 这五个字面量同时出现在五个不同字段里（`LootTable.Type`、`LootOverrideModuleProperties.Overrides[].LootOverride`、`LootOverrideZombossRiftModuleProps.Entries[].Drop`、`PickupCollectableTutorialProperties.LootType`、`ZombieCarnieMonkeyProps.CoinType`），但**没有任何一行**把 Type 映射到 `CollectableType`。本表因此按命名约定映射，并给每一行打 `mapping="inferred-name-convention"` 加一句 `mappingNote`（写明这条约定推导出哪个拾取物、值从哪个字段读、或为什么推不出来）；`EgyptKey` 找不到对应拾取物 → `mapping="unresolved"`。

- pinata **没有内容物**：`pkg_2066_PinataType.json` 39 行只有美术字段（`PinataPopAnim / PinataResGroup / Thumbnail / QuestIcon / PinataOffsets`）。`FirstRewardType=pinata` 给出的只是 pinata 名字，开出什么由服务端结算。

## §7 哨兵统计（`counts.sentinels`）——两套口径，两个数，不可互换

`sentinels` 里有**两组数**，遍历方式与计数值都不同。读它的人必须先看 `scope` 再引用数字（审计 L2，见 §11）。

### 7.1 读路径（`readPathTotal`，白名单遍历）

| 哨兵 | 出现次数 | 出现位置 |
|---|---|---|
| `-1` | 3 | `LootConfig.LevelLength`（`DefaultLoot` / `DangerRoomLoot` / `WhackLoot` 各 1，表「不限长度」） |
| `0` | 35 | `PresentTable.Weight` 28（shiny 里被关闭的 7 条 × 4 世界）、`RiftZombossRewards...AwardQuantity` 6（difficulty 4 档的第 2/3 条奖励 × 3 个 attempt）、`ProgressionRewards[0].Attempt` 1（第一个 attempt 编号就是 0） |
| `2147483647` | **0** | 奖励表里没有出现；本模块仍把 `SENTINELS=(2147483647,-1)` 保留在 `check()` 里，出现即报错 |
| **合计** | **38** | `readPathTotal` = 3 + 35 |

遍历方式：**固定字段白名单，不递归**。白名单 6 类原样写在 `scope.readPath.whitelist` 里：`LootConfig.LevelLength`、`LootTable.Entries[].{Min,Max,Period}`、`PresentTable.Entries[].Weight`、两张 rift 表里所有 `Award*` 叶子、`AwardConfig.GiftBoxRewards[].{AwardQuantity,Probability}`、`GamePropertySheet` 的 5 个经济常量。实际命中的标签另记在 `scope.readPath.fieldsWithHits`（9 个）——分开写，免得「读过了但是干净」被误读成「根本没读」。`0` 在这里要计入：这些字段里 `0` 就是「没有」（`Weight 0` = 关闭、`AwardQuantity 0` = 空奖励）。
`0` 在 `PresentTable.Weight` 里是**关闭**语义（该条目永不掉落），在 `AwardQuantity` 里是**空奖励**语义（该档只有金币、另两条是 0）。两者都保留原始行、不并入任何合计，`counts.sentinels.byField` 给出逐字段计数与样例。

### 7.2 全量递归（`fullRecursive`，无白名单）

| 范围 | `-1` | `2147483647` | 合计 | int / float |
|---|---|---|---|---|
| 本表所读的 10 张包（`readPackages`） | 548 | 56 | **604** | 582 / 22 |
| 全部 2117 个包（`allPackages`） | 4597 | 730 | **5327** | 5298 / 29 |

遍历方式：**每个 objdata 的每个 int/float 叶子，dict 与 list 深度优先，不设白名单**。这里**不统计 `0`**：`0` 在 objdata 里是合法值（冷却、概率、网格坐标），递归统计无法区分「没有值」与「值就是 0」——这正是读路径要单独计 `0` 的原因。

### 7.3 为什么 38 / 604 / 5327 不是同一个数

- **38 → 604**：读路径只看 7 处字段；同 10 张包里还有 `EffectObject_DamageOverTimeProps`（56）、`InitialGridItemProperties`（20）、其他模块字段里大量 `-1`，编译器根本不读它们，所以不进任何合计。
- **604 → 5327**：剩余 1900+ 个包（尤其 `SeedBankProperties` 与波次管理类）也带 `-1`，本表不读这些包。
- **int-only 复算会少 29（=22+7）**：`-1.0` / `2147483647.0` 也是哨兵，`byType` 把 float 单列，任何只数 int 的重算都会低这一点（这一条正是审计 L2 指出过的同类陷阱：口径不同 → 数字不同 → 看起来像错）。

`counts.sentinels.difference` 把这四个数字与 float 拆分写成一句话，`--check` 会验证 `readPathTotal == sum(totals)` 且两套 scope 都存在。

## §8 引擎可以直接用的最小闭环（建议）

要让 `World` 终局发出 `coin` / `key` 事件，**只需要三组字段**，全部在 `rewards_from_pack.json` 里：

```
1) 关卡内金币（按击杀周期）
   LevelDefinition.Loot → LootConfig.LevelLootKey（"default" / "danger" / "whack" / 无）
   → rewards[] 里 id 前缀 "loot:" 且 lootKey 匹配的行：
       {lootType, amount(单次价值), drops[min,max], period, periodUnit}
   每击杀累计 kills；kills % period == 0 时发 coin += amount * rand(drops)

2) 钥匙（按世界 + 进度）
   同 "loot:" 行，kind=="key"：
       world（egypt/pirate/cowboy/future）、condition（"egypt3"）、period 30
   进入世界后该世界的 key 行才启用；进度未到 egypt3 时整条不启用。

3) 关卡通关金币
   LevelDefinition.NormalPresentTable → rewards[] 里 "present:" 行（variant="normal"，weight>0）
       amount（=100）→ 每次通关发一次

4) 南瓜/种子包（可选，僵尸死亡）
   关卡同包内的 ZombieDeathSeedDropModuleProperties：
       dropChance、dropOnAllZombieTypes、SeedDropList[].{PlantType, Weight}
   每次僵尸死亡 roll 一次，命中则按权重选 PlantType 发一个种子包
```

三个字段的出处：`PresentTypeCoin.CoinValue`、`LootTable.{Type,Min,Max,Period,LevelLootKey}`、`GamePropertySheet.CoinsPerKey`；种子包追加 `ZombieDeathSeedDropModuleProperties.{DropChance,SeedDropList}`。
三条工程约束：

- **不要用 `UniqueId` 当主键**（跨 LootConfig 复用），用 `id`；
- **`Period` 是击杀数不是秒**，只有 `whack` 两条是秒（`periodUnit` 已标注）；
- **`Type` 到拾取物没有映射表**，金额来自本表的 `amount`（按命名约定解析 `Collectable*Value`），引擎不必自己再解析 `pkg_0010`。

## §11 审计更正（2026-11-24）

来源：`docs/reviews/2026-11-24-mechanics-rewards-audit.md` 的 **M2**（审计正文里的编号 M3）与 **L2**。两项都只改本模块的 4 个文件。

### 11.1 M2：5 行拾取物映射从 `none` 补成真实拾取物

**改前**：`loot:LawnMower1..4:any` 与 `loot:Sprout1:any` 五行是 `mapping="none"`、`pickup=null`、`unitSource` 指向 LootTable 自身——因为 `LOOT_PICKUP` 只登记了 5 个带数值字段的拾取物，mower/sprout 落到 `else` 分支里当作「无法映射」。

**依据（直读 `pkg_0010_CollectableType.json`）**：
- `lawn_mower`：`objclass="CollectableType"`、`CollectableClass="CollectableLawnMower"`、字段 `Dimensions{75,75}`、`Scale 0.5`、`StandaloneImage "IMAGE_EFFECTS_CARDS_MOWER"`、`GroundSound "Play_GrassStep"` —— **无数值字段**。
- `sprout`：`objclass="CollectableType"`、`CollectableClass="CollectableSprout"`、字段 `PopAnim "POPANIM_ZEN_GARDEN_SPROUTDOOBER"`、`CollectSound/ GroundSound`、`RewardDoFancyCollect true`、`Scale 1.5` —— **无数值字段**。

两者都真实存在，且命名约定（`LawnMower→lawn_mower`、`Sprout→sprout`，与 `GoldCoin→coin_gold` 同一条规则）本可直接推出，所以不存在「约定不适用」的情况。

**改后**：`LOOT_PICKUP` 新增两项，第三元素写 `None` 表示「有行、无数值字段」，于是同一段代码给出：

| 行 | `pickup` | `mapping` | `amount` | `unitSource` |
|---|---|---|---|---|
| `loot:LawnMower1..4:any` | `lawn_mower` | `inferred-name-convention` | 1 | `pkg_0010_CollectableType.json:objclass=CollectableType/lawn_mower (no value field)` |
| `loot:Sprout1:any` | `sprout` | `inferred-name-convention` | 1 | `pkg_0010_CollectableType.json:objclass=CollectableType/sprout (no value field)` |

`amount` 保持 1（一次掉一个），`amountRange` 与 `kind`（`mower`/`sprout`）都不变，因此**经济合计一分未动**；变的只是「掉什么」这件事从 null 变成了有名字的拾取物。

**行数与计数**：`rewards[]` 575 行不变；`mapping` 计数 **18 inferred / 2 unresolved / 5 none → 23 inferred / 2 unresolved / 0 none**。同时新增逐行 `mappingNote`（575 行中 25 条 loot 行有），把「这条约定推出哪个拾取物、值从哪读、或为什么推不出」写在行上；`EgyptKey` 的 `mappingNote` 明确写「`pkg_0010` 只有 worldkey_beach…worldkey_pirate，没有 worldkey_egypt」。`--check` 现在会拒绝「有 `mapping` 却无 `mappingNote`」的行。

### 11.2 L2：哨兵统计口径写清（两个数 + 差异原因）

**问题**：`counts.sentinels` 原来只有 `totals` / `byField` / `examples`，读者无法知道「38」是白名单读路径还是全量递归；另一个模块（`2026-11-24-level-mechanics.md:64`）里「哨兵 264 处」被审计指为读路径统计、全量递归为 1970（全 `-1`），是同一类口径陷阱。

**改法**（本模块范围内，不动 `mechanics.py` 与 `level_mechanics.json`）：

1. `sentinels.scope` 显式写出两套遍历：`readPath`（固定 7 处字段、不递归、计 `-1/0/2147483647`、并说明为何 `0` 要计）与 `fullRecursive`（每个 objdata 每个叶子、深度优先、只计 `-1/2147483647`、并说明为何 `0` 不计）。
2. `sentinels.readPathTotal` = **38**（`-1` 3 + `0` 35），并成为 `--check` 的不变量（必须等于 `sum(totals)`）。
3. `sentinels.fullRecursive` 给两个范围：`readPackages`（本表读的 10 张包）= **604**（`-1` 548 + `2147483647` 56）；`allPackages`（全部 2117 包）= **5327**（`-1` 4597 + `2147483647` 730）。两者都带 `byType`（int/float 拆分）、`byPackage`、`topObjclasses`、`examples`。
4. `sentinels.difference` 一句话写清差在哪：字段白名单 vs 全量、`0` 政策不同、以及 int-only 复算会少的 float 数。

**为什么这三个数都对**：38 是「编译器实际读到的字段里的哨兵」；604 是「同样 10 张包里被忽略字段的哨兵」；5327 是「全库 objdata 的哨兵」。`allPackages` 的 int-only 复算是 5298，差的 29 = 22 个 float 读路径包内 + 7 个 float 其他包——审计 L2 的 264/1970 也是同一种差额（264 = `Stats.num()` 读到的，1970 = objdata 递归），只是那个数在 mechanics 侧、不在本表。
