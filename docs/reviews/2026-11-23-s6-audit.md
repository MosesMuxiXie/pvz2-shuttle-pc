## 3. 发现

### H1 — `--worldmap` 把 `clearedLevels` 硬写成 0，世界地图在 CLI 上永远不会 `completed`
`native/src/main.cpp:264-265`

```cpp
const pvz::map::WorldStatus status = map.status(world.id, progress.totalStars(),
                                                progress.keys, 0);   // <- 0 是字面量
```

复现：见 §2 H1（存档由 175 条 `frontyard_1..175` 的 `cleared=true` 组成，`stars=350`）。
输出同时打印 `"clearedLevels":175` 与 `"state":"available"`，**同一份 JSON 自相矛盾**；26 个世界 1 个 available、25 个 locked，0 个 completed。

影响：模型层没问题（`worldmap_test.cpp:126` 用 `status("frontyard",40,0,frontyard->levels)` 断言过 completed），桌面视图也算对了（`worldmap_view.cpp:152-157`）——**错的正是这个自称「证明模型接到了真实调用方」的 CLI**。任何用 `--worldmap` 验证完成态/解锁链的检查都会得到「永远没通关」，而 CLI 顶部的 `clearedLevels` 又告诉你通关了。S6.4 若把 `--worldmap` 当存档读回的自检，会直接误判。

修法：照 `worldmap_view.cpp:152-157` 的方式按世界前缀数一遍（并对 `levels` 取 min 夹紧），或给 `WorldMap::status` 加一个接 `const Progress&` 的重载，让两个调用方共用同一段计算。

### H2 — 门禁的 `Get-TreeStamp` 看不到它实际测量的 `content/` 与 `native/generated/`
`tools/check_all.ps1:196-209`

```powershell
$roots = @('native/src', 'native/tests', 'native/CMakeLists.txt', 'tools')
$exts  = @('.cpp', '.hpp', '.inc', '.py', '.ps1', '.txt')
```

三点事实：

1. roots 只有源码；`content/**`（1 809 个关卡 + `stars.json` + `world_gates.json`）、`native/generated/**`（smoke 基线、族表、content.pack）、`docs/**` 都不在内。实测 `CONTENT_IN_ROOTS=False`。
2. `.inc` 过滤是死代码：全仓两个 `.inc`（`native/generated/plant_family_table.inc`、`native/generated/zombie_family_table.inc`）都在 roots 之外，永远扫不到。
3. stamp 机制本身是好的：只改一个文件的 mtime，stamp 从 `7802A2E9A3B5E6B6` 变到 `67BF1516103C4CC2`，改回来又复原。

影响：门禁在跑 content → smoke → parity → world_diff 的 ~3 分钟里，若有人改 `content/stars.json` 或重生成 `native/generated/*`，脚本照样 `[ok] … exit 0`，而各步骤读到的是新旧混合的数据。stamp 那句 `[warn] the source tree changed while the gate ran` 说的正是这件事，只是它看不见数据。收敛前的审计基线尤其危险：S6 之后 `native/generated/*` 是多人并行重生成的。

修法：把 `content` 加入 roots；`native/generated` 因 `content` 步骤会重写，单独处理——在 content 步骤之后取一次 stamp、在 finally 再取一次，或者把「允许变化」的路径做成显式白名单并在摘要里打印。顺带把 `.inc` 过滤留给真正会被扫到的目录。

### M1 — `requiredStars` 以 `entryStars > 0` 判「有没有门槛」，`hasEntryGate` 也不是文档说的那个事实
`native/src/worldmap.cpp:191-195,216-224,244-247`；文档 `native/src/worldmap.hpp:60-63`

```cpp
world.entryStars = gate.stars; world.hasEntryGate = true;   // 只在 kind==star && gate.hasStars 时执行
...
if (world->entryStars > 0) return world->entryStars;
if (!world->keyRequired) return world->unlockCost;
return 0;
```

数据侧：97 条 gate 里 **21 条 star gate 的 `stars` 是 0**；41 条 `*_stargate_start` 里 **17 条根本没有 `stars` 字段**（beach/eighties/dino/renai/heian/plantagenet…）。

后果：(a) hpp:60-63 承诺「0 星 gate 与没有 gate 是不同事实、必须可区分」，实现里两者都退化成 `entryStars==0`，不可区分；(b) 一个「有 gate 且 sheet 写 0 星」的非 key 世界会返回 client 的 `unlockCost`，而 `status()` 仍按 `hasEntryGate` 标 `starsSource="sheet"` —— 标签说 sheet、数字来自 client。当前 25 个非 starter 世界恰好全 `key_required=true`，所以 (b) 还没现形，但这是数据巧合，不是不变量。

修法：`requiredStars` 用 `hasEntryGate` 判，把「gate 存在但无 stars」表达成独立状态（`std::optional<int>` 或 `starsSource="gate-without-stars"`）；`starsSource` 的赋值与 `requiredStars` 的来源同源，别各算各的。

### M2 — 视图按「存档键前缀」数 `cleared`，不校验关卡是否真的存在
`native/src/worldmap_view.cpp:152-157`

```cpp
int cleared = 0;
for (entry : progress.levels) { if (!entry.second.cleared) continue;
  if (entry.first.rfind(world.id + "_", 0) == 0) ++cleared; }
statuses.push_back(map.status(world.id, progress.totalStars(), progress.keys, cleared));
```

影响：存档里出现 `frontyard_bogus` 这类键，就能把这个世界的 `cleared` 顶到 `levels` 以上，直接翻成 `completed`；同理 `Progress::clearedLevels()`（CLI 顶部那个数）也会虚高。存档是用户可写文件，`loadProgress` 只校验 JSON 形状，不校验键名。

修法：与 catalog 的关卡集合取交集再计数，并把 `cleared` 夹到 `[0, levels]`。

### M3 — `worlds()[selected]` 无空保护（4 处）
`native/src/worldmap_view.cpp:204,237,264,320`

`WorldMap::load` 允许 `"worlds": []`（只拒绝非数组/缺文件），此时 `worlds()` 为空，`selected` 初值 0，`operator[]` 越界是 UB。桌面构建里只在「空地图 + 有 UI」时触发，等于给未来加世界地图编辑器留了个坑。

修法：`if (map.worlds().empty()) { 画一屏「no worlds」并 return; }`，或在 `runWorldMapScreen` 入口直接抛。

### M4 — replay 的负 `tick` 静默变成 1.8e19，输入永不生效、连 `input_late` 都不记
`native/src/engine/replay.cpp:32`（`input.tick = static_cast<std::uint64_t>(number(entry,"tick",0))`）、`:37-38`（`id`/`id2` 同样无校验）

实测见 §2 M4：`tick:-5` 的种植输入被完全丢弃（`sun` 150 不变），`tick:0` 正常扣费（50）。整个流程没有事件、没有 stderr、退出码 0。

对照：同一文件 `:51-55` 已经为 `collect` 的负 `id` 抛错、`:43-50` 拒 `feed/fuse` 的 `id==0`——说明「输入 id/tick 必须非负」这个规则团队是认的，只是没覆盖 tick。

修法：`tick`、`id`、`id2` 在读入时统一走 `requireNonNegative`，与 collect 同一条错误路径；顺带堵住 `id > INT_MAX` 的窄化。

### M5 — `runScript` 不校验 `seconds`，`--seconds -5|nan` 会跑完整一局
`native/src/engine/replay.cpp:117-125`（`const auto limit = static_cast<std::uint64_t>(seconds / World::stepSeconds + 0.5);`）

实测见 §2 M5：`-5` 与 `nan` 都得到 `tick=8038,status=lost` 的完整战斗，退出码 0。`World::advance` 有 `finite in [0, 86400]` 的检查（`world.cpp:63-65`），CLI 的 `std::stod`（`main.cpp:143`）和 `runScript` 都没有——**同一个量在两处被信任，一处校验、一处不校验**。

影响：脚本/自动化把纳秒或负值传进来时会得到「跑了一整局」而不是报错；`nan` 走的是 double→uint64 的越界转换（C++ 未定义行为），换个编译器/优化级别结果可能不同。

修法：把 seconds 的校验提到 `runScript` 入口（或抽 `ticksFor(seconds)` 复用 advance 的规则），CLI 侧拒绝非有限值。

### M6 — projectile 表 rows≠entries：`MangosteenPlantFoodDefault` 出现两次，两个计数口径混用
`native/src/engine/projectile_table.cpp:131-134`

```cpp
if (spec.hasSplash) ++table.withSplash_;      // 按「行」累加
if (spec.hasPierce) ++table.withPierce_;
table.specs_.insert_or_assign(std::move(id), std::move(spec));   // 按「id」去重（后者覆盖前者）
```

实测数据：`native/generated/projectiles_from_pack.json` **602 行 / 601 个唯一 id**，重复的是 `MangosteenPlantFoodDefault`；出厂的 `native/generated/projectile_report.md` 也按 602 计分母（`splash 217/602`、`pierce 41/602`）。

后果：`withSplash()`/`withPierce()` 是行数，`size()` 是 id 数 —— 任何把两者相除的报告都会得到 >1 的比率或差一；重复行静默覆盖（哪一行赢取决于顺序），而 catalog 对重复 id 是抛错的（`catalog.cpp` 有 unique 校验），这里没有。

修法：重复 id 抛错（与 catalog 一致）；`withSplash_`/`withPierce_` 改成插入成功后按 `specs_` 重算，或干脆改成 `count_if`。

### M7 — 世界门数据里 24 条 gate 挂在不存在的世界上（含 `kungfu` / `kongfu` 拼写分叉）
数据 `native/generated/world_gates.json` + `native/generated/worldmap.json`；口径固定在 `native/tests/worldmap_test.cpp:26-54`（断言 `gates==97`）

- 97 条 gate 中，**24 条的 `world` 不是 26 个客户端世界之一**；其中 `kungfu_stargate_start`（`world=client=kungfu`）与 `kongfu` 只差一个字母，`worldgate_kungfu` 的 `target=kungfu` 同样是悬空目标。
- `WorldMap::gateCount(id)` 只统计挂靠上的 gate，所以这些行永远影响不到任何世界，却计入 `gates()` 的 97，并被 `testShape` 当成契约固化。

影响：「97 门」这个数字被引用为 S6.1 的达成度，其中约 1/4 是模型永远不会用到的行；`kongfu` 的门因此永久失效，而测试因为只断言总数不会发现。

修法：生成器合并拼写（`kungfu`→`kongfu`）或把不挂靠的行单列；模型暴露「已挂靠/未挂靠」两个数，`testShape` 断言两者之和等于 97 并断言未挂靠集合为空。

### L1 — `cowboy` 那条星章断言「通过的理由是错的」
`native/tests/worldmap_test.cpp:73-79`

断言 `cowboy` 的 `requiredStars==0 && starsSource=="sheet"`。但 `cowboy` 是 key-gated，`requiredStars` 在 `entryStars==0 && keyRequired` 时直接返回 0（M1 的第二个分支），所以**这条用例无法区分「sheet 真的支持 0 星门槛」与「根本没有 stars 信息」**。真正保护 sheet 分支的是同文件里 lunarrainbowmarket 的 10 星那条。

修法：新增一条断言 `hasEntryGate==true && entryStars==0`（用 21 条 0 星 gate 中的一条），或直接断言 `starsSource` 的来源与 `entryStars` 一致。

### L2 — 渲染测试两条弱断言
`native/tests/worldmap_render_test.cpp:75`（`check(result.unlocked >= 1, "a fresh save must still open the first world")`）、`:91`（`check(fs::file_size(again) == fs::file_size(root / "worldmap.png"), ...)`）

- `unlocked >= 1`：全部世界都解锁时也过，测不出「starter 规则失效」。
- 只比文件大小：两张完全不同的 PNG 只要等长就通过。

修法：断言 `unlocked == 1 && completed == 0`（新存档的精确形状）；第二次运行比字节或哈希（`Get-FileHash` 等价物：读文件比对）。

### L3 — starter 的判据是死代码
`native/src/worldmap.cpp:195`：`world.starter = map.worlds_.empty() ? false : (i == 0);`

循环体内 `worlds_` 必非空，`empty()` 分支永远不执行；实际语义是「排序后第一个」，frontyard 只是因为 `order=1` 恰好排第一。若将来 order 重排，starter 会静默换人。

修法：去掉空判据，改成显式 starter id（`content/worldmap.json` 里加字段），或断言 `worlds.front().id == "frontyard"`。

### L4 — 进入的关卡取「字典序第一」
`native/src/worldmap_view.cpp:104-110,207,304`：`levelsOf()` 排序后取 `front()`。`frontyard_1` 只是恰好是 `frontyard_10` 的前缀，才被选中。已核对 26 个世界都有 `<world>_1.json`，所以当前正确；缺 `_1` 的世界会开错关。

修法：优先精确匹配 `<world>_1`，否则按 `index` 数值排序取最小。

### L5 — `-NoDesktop` 时不核对台账的 desktop 行，脚本仍可能 `[ok]`
`tools/check_all.ps1:313`（`if (-not $NoDesktop) { $measured['desktop'] = ... }`）+ `:239-258`（只遍历 `$measured`）

本次审计的两次门禁都是 `-NoDesktop`，因此 ledger 里 `| desktop | 25 |` 这一行**从未被验证过**，而脚本的输出仍会给出 `[ok] content, build, tests and parity are consistent`。

修法：`-NoDesktop` 时打印 `[skip] desktop ledger row (no desktop build this run)`，并在最终摘要里列出「本次未核对的行」。

### L6 — 失败优先于 stamp：树红时永远看不到 `[inconclusive]`
`tools/check_all.ps1:353-367`（`if ($failures.Count -gt 0) { exit 1 }` 在 stamp 比较之前）

实测：09:06 在真仓跑 `check_all.ps1 -NoContent`，并在 40 秒处 metadata-only touch 了 `native/tests/worldmap_test.cpp`，输出只有 `[fail] audit build (exit 1)`，没有任何 `[warn] … changed` / `[inconclusive]`。语义上保守（失败优先），但把「某人正在改、所以构建失败」呈现成「你的门禁坏了」，正是 stamp 想要的场景被跳过。

修法：失败分支里附一行 `stampStart != stampEnd ? "note: the tree changed during this run" : ""`，不必改退出码。

### L7 — armor 表：计数双分母 + 一个会把「真的 0」改写的兜底
`native/src/engine/armor.cpp:146`（`table.specs_.emplace(...)` 静默丢重复 id）、`:197`（`if (table.unused_ == 0) table.unused_ = table.unusedIds_.size();`）

- 当前 102 行 / 102 唯一 id，没有重复；但 `emplace` 语义是「重复就丢」，与 catalog 的抛错策略不一致。
- `unusedArmors=0` 会被改写成 `unusedArmorIds` 的长度：一个真的 0 变成 N。
- `counts.danglingReferences=13` 与 `dangling` 数组的 3 行是两个不同分母（引用数 vs 唯一 id 数），访问器都叫 dangling，报告里容易搞混。

修法：重复 id 抛错；删掉 `unused_==0` 的兜底；访问器改名区分 `danglingReferences()`/`danglingIds()`。

### L8 — 9 行 `trajectory` 落到 `unknown`，没有任何告警
`native/src/engine/projectile_table.cpp:35-41`（`trajectoryOf` 未命中即 `Trajectory::unknown`）

602 行里 `straight=374, arc=118, drop=59, static=42, unknown=9`。`unknown` 不影响载入，只能靠 `trajectoryCount(unknown)` 看到；`spawnShot` 会把 `trajectory` 抄进 shot，但没有任何事件或审计输出。
