## BLOCKER

### B1 跳跃类僵尸往右落地且永不啃食 → 139 张含 `pole_vaulter` 的关卡永不结算

- **证据**：`native/src/engine/registry.cpp:174-189`（关键行 `183: z->x = centre + 1.05;`）把僵尸
  放到植物**右侧** 1.05 列；而僵尸推进是 `world.cpp:145` 的 `zombie.x -= speed * dt`（向左）。于是
  下一 tick 又落进 `178-181` 的判定窗口 `[centre-1.4, centre+0.5]`，再跳回右侧，无限循环。
  同时 `world.cpp:125` 把 `jump` 与 `fly` 一起排除在啃食判定之外，落地后也啃不动植物。
  `extra.jump_distance` 在 `native/src` 内无任何读取点（grep 命中 0）。
- **复现**：上面的 `probe_2`——wallnut 在 (0,4)，一只 `pole_vaulter` 在 row 0：200 s 后
  `status=playing, killed=0`；跑到 4000 s（tick 240000）仍然是 `playing`，僵尸既没死也没进屋。
- **影响**：`content/zombies.json` 只有 1 种 jump 僵尸（`pole_vaulter`，"渡渡鸟骑手"），却被 139 个
  关卡文件引用（`beach_80`、`carnival_12/16/27/33/46/61/67`、`dino_52`、`fairy_28` …）。这些关卡
  在引擎里**不可能赢**：僵尸卡在植物右侧，`resolveOutcome` 的 `zombies_.empty()` 永远不成立。
  烟测和 `engine_test` 都不会碰到（5 个场景 + 26 个世界首关里没有该僵尸的关）。
- **修法**：落地改成往左跨过目标植物，例如 `z->x = centre - (1.0 + jump_distance*0.5)` 或
  `z->x = centre - tuning::kEatStartCols - 0.01`；跳完把 `state` 置 `walking` 并允许啃食（把
  `world.cpp:125` 的例外表缩到只剩 `fly`），并让 `zombieJump` 只触发一次（例如用
  `nextSpecialTick` 或一个 `jumped` 标志），否则会在下一株植物前反复起跳。

## HIGH

### H1 `World::plant` 不校验关卡卡组（deck），旧引擎会拒

- **证据**：`native/src/engine/world.cpp:216-264` 只检查 finished/未知/越界/占位/冷却/阳光，**没有任何
  `level.deck` 判断**；旧引擎 `native/src/simulation.cpp:62-68` 明确 `return "not-in-deck"`。
- **复现**：`probe_1` 的 `deck` 只有 `["wallnut"]`，脚本在 tick 0 额外种了 `peashooter`（cost 100）。
  结果 `sun=825`（1000−75−100）而不是 925 —— 卡组外的植物被接受、扣费、进入世界。
- **影响**：`content/levels/*.json` 的 `deck` 字段在引擎侧形同虚设；任何脚本/UI 错误都能种出卡组
  外的植物，回放与录像的"合法性"不受保护，S3 的选卡界面也就没有权威数据源。
- **修法**：在 `world.cpp:224` 前后加
  `if (std::find(level_.deck.begin(), level_.deck.end(), type) == level_.deck.end()) return "not-in-deck";`，
  并在 `world_outcome_test.cpp` 里补一条 deck 拒绝用例（对着 `sun` 断言，别只断言返回非空）。

### H2 判负挂在"推车状态"上而不是"越线"，且推车触发线用错了常量

- **证据**：`world.cpp:153-162`：僵尸 `x < kLoseX` 时——`state==0` 触发推车、`state==2` 判负、
  **`state==1`（推车正在跑）什么都不做**，僵尸继续往左走。`tuning.hpp:36` 的
  `kMowerTriggerX=-0.25` 在 `native/src` 内**无使用者**（grep 只命中定义），触发与判负都用
  `kLoseX=-0.7`。旧引擎 `simulation.cpp:245-257` 用 `breach = any(z.x < -0.7)` 立即判负，不看推车。
- **影响**：同排两只僵尸时，第二只可以在推车外出期间越线而世界仍报 `playing`，最多延迟约
  `(cols+1+0.5)/8 ≈ 1.3 s` 才判负；这 1.3 s 里"已经进屋"的状态会被写进快照与事件流，回放/录像对不上，
  也给"用推车状态推断胜负"的 UI 留下错窗口。触发线从 -0.25 漂到 -0.7 还意味着推车比原版晚 0.45 列出场。
- **修法**：判负与推车解耦——任一 `alive` 僵尸 `x < kLoseX` 且该排 `mower.state == 2` 就立即 `lost`，
  与 `state==1` 无关；触发线改回 `kMowerTriggerX`，`kLoseX` 只作判负线。

### H3 召唤在 `tickZombies` 的 range-for 内部 `push_back`，随后继续用旧引用

- **证据**：`registry.cpp:206-214` 的 `zombieSummon` 调用 `world.spawnZombie(minion, z->row)`
  （`world.cpp:309` 的 `zombies_.push_back`）；回到 `world.cpp:121` 的
  `for (auto& zombie : zombies_)`，`152-153` 紧接着 `(*behavior)(*this, zombie.id);` 与
  `if (zombie.x < tuning::kLoseX ...)` —— 容器可能已重分配，引用与迭代器都悬垂（UB）。
- **影响**：`summon` 家族一旦接到真实关卡（pack 里 1127 条僵尸规则、`zombieActions` 目前 0 条已建模），
  Debug 版可能直接崩、Release 版静默读到错的 `x/row`，并且这是"只在特定队伍配置下偶发"的形态，
  最难定位。`-AuditOnly` 没有开 ASAN，现有 10 个用例也不会构造出 400 只僵尸的召唤。
- **修法**：`tickZombies` 改成"先收集这一 tick 要执行的 `(id, family)`，再按 id 逐个执行"，或者在循环
  里用 `zombies_.size()` 快照 + 索引访问；`spawnZombie` 之外所有 mution 都延迟到 `reap` 之后。

### H4 `check_all.ps1` 在比对之前就把基线覆盖掉，回归门禁必然自愈

- **证据**：`tools/check_all.ps1:84-90`——`$beforeSmoke` 读旧文件、`$afterSmoke` 读新文件，
  **第 86 行 `Copy-Item $smokeFresh $smoke -Force` 先执行**，第 87 行才 `Compare-Report`；
  `103-109`（PARITY_MATRIX）、`116-122`（world_diff）是同一套写法。判定不一致只是 `$failures.Add(...)`，
  文件已经变成新值；下次运行自然相等。三个被比对的产物在 git 里全是 `??`（未跟踪），没有回滚来源。
- **实证**：本次审核期间（19:59 我第一次读基线 → 20:07:38 文件被重写 → 20:1x 我实跑）5 个场景的
  `hash` 全部变化（`0x17bdb328fadcdf25` → `0xa76d48ab1cfd2c8f`，`tick` 不变），而
  `python tools/engine_smoke.py` + 与基线的比较结果是 **IDENTICAL** —— 基线已被改写成新值。
  队长自查 #4 引入的哈希字段扩充正是这样"静默改基线"的。
- **影响**：S3 期间任何真实的 hash 漂移都会被吞掉一次然后变成新基线；`-AllowMatrixChange` 这个开关
  在这套写法下失去了意义。门禁只能抓"第一次跑失败"，抓不到"上一次跑完之后改动"。
- **修法**：`Compare-Report` 在 `Copy-Item` **之前**完成（先 `if (不同 && !$AllowMatrixChange) { 不覆盖 + fail }`），
  或者新值写 `build/`、只有 `-Accept` 才落到 `native/generated/`；并把三份产物纳入 git（或至少
  `git add -N`），让 diff 可审。

### H5 减速时长把"秒"当"tick"用，减速几乎不存在

- **证据**：`native/src/engine/projectile.cpp:35`
  `zombie.slowUntilTick = static_cast<double>(world.tick()) + shot.slow;`——`shot.slow` 来自
  `world.cpp:245` 的 `action.chillDuration + action.freezeDuration`（**秒**，且两者相加本身也可疑：
  chill 与 freeze 是两段语义），而 `world.cpp:144` 的判据是
  `zombie.slowUntilTick > static_cast<double>(tick_)`（**tick**）。
- **影响**：3 秒的减速只持续 3 tick（50 ms），冰冻同理；冰系植物在数据驱动路径上等于没有控制效果。
  这个字段同时参与 `hash()`（`world.cpp:509`），所以哈希稳定，测试与烟测都看不出来。
- **修法**：`world.tick() + ticksOf(shot.slow)`；`shot.slow` 改成 `std::uint64_t`，字段名 `slowTicks`
  以免再次单位混用；chill 与 freeze 分开两个字段（freeze 应该禁走/禁攻击，而不是 0.5 倍速）。

## MEDIUM

### M1 `advance()` 没有输入校验：一次 NaN 就永久冻结，单位超出预算则静默丢时间

- **证据**：`world.cpp:57-67`。`if (seconds <= 0) return;` 对 NaN 为假 → `accumulator_ += NaN` →
  `while (accumulator_ + 1e-12 >= stepSeconds)` 恒假、`if (accumulator_ < 1e-12)` 也恒假，
  `accumulator_` 永久是 NaN，此后每次 `advance()` 都推进 0 tick（不报错、返回 `void`）。
  另外 `guard < 200000`（≈3333 s）会静默截断，未消费的时间留在 `accumulator_` 里，下一次 `advance()`
  会立刻再烧掉 200000 步。旧引擎 `simulation.cpp:8-12` 对 `!isfinite || <0 || >86400` 直接抛异常。
- **影响**：S3 的桌面循环只要有一帧 `dt` 算出 NaN/Inf，世界就静默停摆（观感是"游戏卡死"）；
  库使用者也无法发现时间被吞。CLI 路径不受影响（`replay.cpp:80` 直接 `step()`），所以现有门禁
  一条都测不到。
- **修法**：入口加 `if (!std::isfinite(seconds) || seconds < 0 || seconds > 86400) throw std::invalid_argument(...)`；
  截断改为返回实际推进的 tick 数（`std::uint64_t advance(double)`）或把余量清 0 并记事件。

### M2 胜利"宽限"是死代码；死亡淡出永远不可能被观察到

- **证据**：`world.cpp:205-213`——`if (!director_.allSpawned()) return;` 已经蕴含
  `cursor_ >= schedule_.size()`，也就是 `tick_ >= lastTick`，于是 `209-210` 的
  `tick_ + flush < lastTick()` 恒假，`kVictoryFlushSeconds`（`tuning.hpp:33`）不起任何作用。
  队长自查把语义写成"等最后一波 spawn 游标越过 lastTick"，但这句条件在 `allSpawned()` 之后必然成立，
  代码无法表达"等"。
  另一半：`damageZombie` 置 `state=dying`/`deathTick=tick_` 后，`reap()`（`189-195`）在**同一个 tick**
  就把 `!alive` 的僵尸 erase 掉，`tuning.hpp:25` 的 `kZombieDeathFadeSeconds=0.3` 全项目无使用者，
  `Snapshot`（`548-551`）也没有 `dying/deathTick` 字段。
- **影响**：`resolveOutcome` 看起来有 0.5 s 的收尾窗口，实际没有（读代码的人会误判胜利时机）；
  渲染层拿不到死亡动画（0.3 s 淡出无法实现），S5 的"最后一只僵尸倒下"表现只能靠事件流补。
- **修法**：宽限若真需要，就把判据改成"最后一只僵尸死亡后 N tick"（记 `lastKillTick_`）；
  死亡淡出要么在 `reap` 里按 `tick_ - deathTick >= ticksOf(0.3)` 延迟回收，要么删掉常量并承认
  "死亡不可见"，同时给 `ZombieView` 加 `dying`。

### M3 有槽位的植物整段跳过 family 行为，"接线"口径因此虚高

- **证据**：`world.cpp:103-117`——`if (!plant.slots.empty()) { runActionSlots(*this, plant); continue; }`，

  **完全没有攻击**，而矩阵显示 100% 接线。`wired` 与 `playable` 分开后这个偏差被"0.0% 可玩"掩盖了。

### M4 `hash()` 仍未覆盖全部"决定未来"的字段（自查 #4 的残留）

### M6 关键用例的断言不能失败：`testTwentySixWorlds` 恒真，`testShotsAndEating` 不测啃食

- **证据**：`native/tests/engine_test.cpp:110-112`——
  `check(status == "playing" || status == "won" || status == "lost", ...)` 覆盖了 `status` 的全部取值，
  `check(instance.hash() != 0, ...)` 对 FNV-1a 实际恒真（`1469598103934665603` 起步，非零输入不会回 0）。
  即 26 世界用例只能抓崩溃。
  `132-141` 的 `testShotsAndEating` 名字里有 eating，但既不摆僵尸啃植物的场景，也不断言植物掉血；
  `hurt` 是三个条件的 OR（`killed>0 || zombies 空 || 首只 hp 下降`），任何"豌豆真的打到"都满足。
  没有任何用例断言推车触发/判负（H2 因此无人发现）。`188-191` 的 `argc < 4` 要求第三个参数
  `<temp>`，但 `wmain` 里 `argv[3]` **从未使用**（`CMakeLists.txt:108` 照样传）。
- **影响**：这三处让"engine 用例通过"这件事对语义几乎没有约束力；S3 的接线回归只能靠人眼。
- **修法**：`testTwentySixWorlds` 改成断言"每关至少推进 N tick 且 hash 三次一致"或直接断言

  恰好减少 `eatDps * dt * 60`；补 `world_outcome_test` 的推车/判负用例；`<temp>` 要么用起来
  （写快照/回放文件）要么从 `argc` 契约里去掉。

### M7 两套引擎并存且关键数值分叉，桌面端跑的不是被审核的这套

- **证据**：`main.cpp:2` 仍 `#include "engine/replay.hpp"` 且 `simulation.hpp` 也在用；

## LOW

### L1 `kMaxPlants` 无使用者，植物没有上限
`tuning.hpp:50` 定义 200，全项目 grep 只有定义处；`world.cpp:216-264` 无上限检查，而僵尸
（`286-288`）、子弹（`spawnShot`）、阳光（`spawnSun`）都有。**修法**：加 `if (plants_.size() >= kMaxPlants) return "too many plants";`。

### L2 `removed` 恒为 0，`killed` 把推车碾压算作击杀，且没有"漏怪"计数
`world.cpp:388-399` 的 `removeZombie` 是 `removed_` 的唯一写入点，而生产路径（tick/waves/replay）里
没有任何调用者——三次探针的 `removed` 都是 0。推车击杀走 `damageZombie` → `++killed_`（`180`），
与豌豆击杀混计；`spawned_ - killed_` 无法区分"还活着"和"已进屋"。**修法**：给推车单独记
`mowerKills_`，给越线记 `leaked_`，`summarize` 一并输出。

### L3 回放输入允许"迟到"，`collect id=0` 与真实 id 0 冲突
`replay.cpp:53` 的 `while (cursor < ... && script.inputs[cursor].tick <= world.tick())` 让任何过去时刻
的输入照样生效（写错 tick 不报错）；`63-67` 把 `id == 0` 解释为"收下所有阳光"，于是 id 恰为 0 的
那一颗无法单独指定。`32` 把 JSON 的 `tick` 直接 `static_cast<uint64_t>`，负数/超大值会绕成巨大 tick。
**修法**：输入按 tick 严格大于当前 tick 才接受（过期记 `input_late` 事件）；`collect` 用
`op: "collect_all"` 显式区分；解析时校验 0..86 400*60。

### L4 `--rows/--cols` 缩小时静默丢僵尸
`world.cpp:85` 对 `spawnZombie` 失败直接 `continue`，而 `286-288` 的边界检查会拒绝
`row >= rows_` 的刷新；`--rows 2` 跑 `frontyard_1` 会少刷而那几波的行号本来就在 `spawn.rows` 里。
**修法**：`tickWaves` 里对首刷失败记 `wave_spawn_rejected` 事件并在 `summarize` 里计数，别只 `continue`。

### L5 `parity_report` 的 `playable` 是字面量 0，与"数字来自磁盘"的声明矛盾
`tools/parity_report.py:177/185/193/201/209`（植物/僵尸/世界/关卡/融合…的每一行）全部 `playable=0`，
`73-74` 于是所有完成度恒 0.0%；
docstring `4-12` 却写"Every number is derived from files on disk, never from constants"。
`92-98` 的 `engine_families` 在 `registry.cpp` 缺失时返回**空集**（fail-open），会让 `wired` 变成
0/0 而不是报错。**修法**：`playable` 从 `native/generated/engine_smoke.json` 的 `status=="won"` 计数
推导，或把该列改名为"待统计"并置空；`engine_families` 找不到文件时抛异常。

### L6 `tools/build_native.ps1` 固定 `build/native`，并发构建互相踩
`build_native.ps1` 在 `-AuditOnly` 下固定用 `build/native`，两个成员同时跑就撞
`MSB6003 ... CL.read.1.tlog ... being used by another process`（本次审核第一次 `-AuditOnly` 即失败）。
**修法**：目录带参数（`-BuildDir`）或按进程 id 临时目录 + 最终产物软链到 `build/native/Release`。
