## 0. 结论速览

1. **451.0 与 451.2 是同一份代码的两个渠道包。** 两者字符串差集只有 `+2 / −1`（唯一的实质差异是版本字面量 `451.0` ↔ `451.2`）。后文所有对比以 **460.11 vs 451.0** 为主，451.2 的结论与 451.0 相同。
2. **460.11 不是 EA 官方流水线产物。** 证据：`.comment` 用 clang **17.0.2 (+pgo,+bolt,+lto)** + LLD 17.0.2（451 用 clang 18.0.1/12.0.9 + LLD 12.0.9）；`e_entry = 0`（451 为 `0x19A044`）；且出现源码路径 `D:/HookPVZ2/czProj/x64/jni/PvZ2/src/…`（451 里是 `/opt/scm/jenkins_root/…`）。可判定为**基于抓到的源码树在本地重编的构建**。
3. 规模：`.text +254,532 B (+8.7%)`、`.rodata +26,752 B (+30.7%)`、`.data.rel.ro +36,288 B (+11.2%)`、文件 `+382,168 B (+7.7%)`。
4. **JNI 导出面完全没变**：349 个导出符号名字集合逐字节一致；导入 `+30 / −7`（净 +23，`.dynsym` 恰好 +552 B = 23×24 B）。
5. 字符串层：**新增 873 条、消失 165 条**（相对 451.0）。新增重心是 **Roguelike 肉鸽系统(155)**、**元素反应(60)**、**7 个新植物(57)**、**关卡机制字段(42)**、**设置/语言/帧率/沙盒 UI(50)**。
6. 关于"新能力"的五个问题（详见 §8）：
   - 新 rsbpatch 版本？**没有**。仍是 patch format v1（magic `RSBP`）+ before-file 必须 RSB v4，判定分支与 451.0 逐条对应。
   - 新资源容器格式？**没有**。RTON/RSB 装载路径不变；但新增 `roguelike.dat` 与 `.json` 落盘、`QueueRTON redirected`、`WriteWholeFileAtomic`。
   - 新关卡机制类名？**有**：`RogueModule` / `ElementReactionModule` / `SlotMachineModule` 三个 Module 类，`AciditySubsystem` / `VoidDragonNasaSubsystem` 两个 Subsystem，`GridItemIceHole` / `GridItemFireWall` 两个 GridItem。
   - 新世界 id？**没有**。`Poseidon`/`Atlantis` 在 451.0 已存在（`ZombieAtlantisPoseidonSummonActionHandler` 等），460.11 只多了 Poseidon 的调试日志。
   - 新事件名？**有**（Roguelike 战斗事件、元素反应计时键、语言选择事件等，见 §8.5）。
7. **460.9 数据包兼容性：只能给推断**——格式闸门与 451.0 等价（RSB v4 可读），但 **OBB 命名闸门要求 `main.<数字>.com.ea.game.pvz2_shu.obb` 且数字段来自当前 APK 的 `versionName`**，所以"460.11 的 APK + 460.9 的 obb"会先卡在文件名而不是内容版本上。详见 §9（含推断标记）。

## 1. 方法与边界

**边界**：全程只读。未动态执行任何 `.so`，未联网，未改动任何 C++/内容 JSON/生成物；新增文件只有本报告与 `work/versions/` 下的脚本和中间产物。

**工具与流程**：

| 步骤 | 脚本 / 工具 | 产物 |
|---|---|---|
| ELF 结构解析（ehdr/phdr/shdr/`.dynamic`/dynsym/字符串抽取） | `work/versions/_elfscan.py`（纯 Python，无第三方库） | `work/versions/out/{official_46011,apk_4510,github_4512}.json` |
| 字符串集合差集（只取数据段，过滤 `.text` 里的机器码噪声） | `work/versions/_diff2.py` | `work/versions/out/delta2_*.tsv` |
| 功能聚类 | `work/versions/_clusters.py` | `work/versions/out/clusters_46011.md` |
| 报告用字面量表（按组带偏移） | `work/versions/_report_tables.py` | `work/versions/out/report_tables.md` |
| 原始字节复核（防止把数据表/UTF-16 误当字面量） | `work/versions/_probe.py` | 见 §7 校验说明 |
| 交叉引用与反编译 | Ghidra 12.1.4 headless + 自写 `DumpCore.java` | `work/versions/out/core460_dump.txt`(68,484 B)、`core451_dump.txt`、`ghidra_core460.log`、`ghidra_core451.log` |

**地址约定**：本报告所有偏移都是**文件内偏移（file offset）**。`.so` 是 `ET_DYN`，第一个 `PT_LOAD` 为 `p_offset=0 / p_vaddr=0`，故文件偏移 == 链接地址；Ghidra 载入时另加镜像基址 `0x100000`，即 **Ghidra 地址 = 文件偏移 + 0x100000**（例：`460.11` 字面量文件 `0x107A61` ↔ Ghidra `0x207A61`）。

**字符串口径**：ASCII、长度 ≥4、以 NUL 终止、同一版本内去重、只统计落在 `.rodata`/`.data.rel.ro`/`.data`/`.dynstr`/`.note.gnu.build-id` 的条目（`.text` 里被误认的字节序列一律丢弃）。`note.gnu.build-id` 反序列化出的 1 条伪串（`0x2EC`）已从表中剔除。

## 8. 关键能力判定

### 8.1 rsbpatch：没有新版本、没有新格式

Ghidra 反编译两版的同一个函数：`460.11 FUN_002c469c` ↔ `451.0 FUN_002a9618`，判定分支逐条对应（下表变量名直接摘自反编译输出）：

| 检查 | 460.11 | 451.0 | 失败串 |
|---|---|---|---|
| before 头 `fread(...,1,0x70,...)` 必须读满 0x70 | `local_e8` | `local_f8` | `cannot read before file header` |
| before magic == `0x72736231`（`"1bsr"`） | `if (local_e8 != 0x72736231)` | `if (local_f8 == 0x72736231)` | `before file is not a valid rsb (magic mismatch)` |
| before 版本 == **4** | `if (local_e4 != 4)` | `if (local_f4 == 4)` | `before rsb version not supported` |
| patch magic == `0x52534250`（`"RSBP"`） | `if (*__s != 0x52534250)` | `if (*local_228 != 0x52534250)` | `rsbpatch magic mismatch` |
| patch 格式版本 == **1** | `if (__s[1] != 1)` | `if (local_228[1] != 1)` | `rsbpatch version not supported` |
| package info 字段 == **2** | `if (__s[2] != 2)` | `if (local_228[2] != 2)` | `rsbpatch package info unknown_1 check failed` |
| before 的 info-section hash | 与 patch 内记录逐字节比较 | 同 | `rsbpatch check failed: before rsb info-section hash does not match patch` |

两版唯一的区别是**控制流形状**：451.0 用嵌套 `if (magic == …) { if (ver == 4) { … } }`，460.11 改成提前返回 `if (magic != …) { …return… }`；另有字符串构造方式差异（451 用 `operator_new` + 常量拼接，460 统一走 `FUN_002b62b8(&local_200, "...")`）。**判定语义完全一致**。

旁证：rsbpatch 的 **9 条错误串在三版里逐字相同**（只有偏移不同）：

| 错误串 | 460.11 | 451.0 | 451.2 |
|---|---|---|---|
| `rsbpatch package info unknown_1 check failed` | `0x105B9B` | `0xF2B30` | `0xF2B30` |
| `rsbpatch check failed: before rsb info-section hash does not match patch` | `0x107330` | `0xFAD4A` | `0xFAD4A` |
| `rsbpatch data too short` | `0x10B0AC` | `0xF8B1F` | `0xF8B19` |
| `rsbpatch check failed: packet ` | `0x10D6E1` | `0xFB6D8` | `0xFB6D8` |
| `rsbpatch only supports RSB v4, current file is v` | `0x10D73A` | `0xF44AF` | `0xF44A9` |
| `before file is not a valid rsb (magic mismatch)` | `0x10FC18` | `0xF3D6C` | `0xF3D6C` |
| `cannot read before file header` | `0x114A76` | `0xFD800` | `0xFD800` |
| `cannot read before info section` | `0x1161A9` | `0xEEB6E` | `0xEEB6E` |
| `Detected big-endian rsb1 file; rsbpatch only supports little-endian 1bsr format` | `0x1161C9` | `0xF3546` | `0xF3546` |

结论：**patch 容器格式版本仍是 1，before 镜像仍必须是 RSB v4**。460.11 没有引入 rsbpatch v2，也没有引入 RSB v5；连"大端 rsb1 拒绝"这种边角判定都在，说明打补丁链路是**原样继承**而非重写。

### 8.2 资源格式：容器没变，落盘方式变了

## 9. 460.11 是否仍兼容 460.9 数据包

> **本节全部是静态推断，未做任何实机/动态验证**（按任务边界不执行 `.so`、不联网）。

**可确证的事实（来自二进制）**

- E1：`460.11` 的 rsbpatch 闸门与 `451.0` 完全等价 → 只要 before 镜像是 **RSB v4**、patch 是 **format v1**，就能进解码；460.9 的数据包若本身是 RSB v4（其 patch 链 `460.1_460.2.rsbpatch` / `460.2_460.9.rsbpatch` 已在 `work/versions/_incoming/` 内），格式层不设障碍。
- E2：`.so` 内没有"内容版本 == 某值"的比较；内容版本号从 `versionName` 反射得来，且**只用于拼 OBB 文件名**。
- E3：OBB 名合法性检查（`460.11 FUN_002c434c` ↔ `451.0 FUN_002a9408`，同一份源码、不同代码生成）的判定链，两版逐条相同：
  ① `compare(param_1,0,0x5) != 0 → false`（前 5 字节必须是 `main.`）；
  ② `strstr(s,".com.ea.game.pvz2_shu.obb")` 且 `strcmp(...)==0 → false`（后缀必须精确等于该串）；
  ③ `find(param_1, 0x2e)`（找 `.`）：返回 `npos` → false；`== 5` → false；`< 6` → **true**（即 `main..com…` 这种空数字段被放行）；
  ④ 否则从下标 5 到第一个 `.` 逐字节要求是 `'0'..'9'`，最后 `return uVar3 <= uVar5`（整段必须是数字）。
  两版的数字判断写法不同但等价：451 是 `pbVar4[5] - 0x30 < 10`，460.11 是 `0xfffffff5 < pbVar4[5] - 0x3a`（`0x3a-0x30 = 10`，无符号回绕后同一个集合）。
- E4：`no obb data package found to patch` 是这条检查失败后的输出。也就是说**名字不匹配时直接放弃打补丁**，根本走不到内容版本比较。
- E5：460.11 的 Roguelike 默认关闭 —— `ROGUELIKE_ENABLE=0`（`0x10C83B`），且新增键集中在 `roguelike.dat` / `[RL_BUFF_*]` / 元素反应组，这些键在 460.9 数据里不存在。

**推断**

1. **格式可读**：460.9 的 RSB/RTON 数据在 460.11 里仍能被解析（容器、压缩、编码三处闸门都没变）。
2. **但有命名闸门**：若把 460.9 的 `main.<x>.com.ea.game.pvz2_shu.obb` 直接配给 460.11 的 APK，而 `<x>` ≠ 该 APK 的 `versionName`，则第一步就被判为"不匹配"，表现为 `no obb data package found to patch`。**这与"内容版本"无关，是"包版本"问题**；解决办法是把 obb 名改成与 APK `versionName` 一致（或反向改 APK）。
3. **缺键的后果无法从字符串判断**：460.11 新增的 Module（`RogueModule` / `ElementReactionModule` / `SlotMachineModule`）在读到 460.9 数据时属于"模块声明了但表里没键"。是走默认值、跳过、还是硬失败，取决于各 Module 的加载容错，**这需要反编译 `RogueModule::Create`/`Load` 才能定论，本次未做**（列入未知项 U2）。

**一句话**：*格式上兼容（RSB v4 未变），工程上会被 OBB 命名挡住；内容缺键是否致命未验证。*

## 10. 对 S3 工作的可复用点

- **命名参照**：`GridItemIceHole`/`GridItemFireWall`/`CollapseRadiusCells`/`TargetGridRect`/`IceHoleRadius`/`IceHoleCount` 是 460.11 的**新几何/网格参数字段名**。S2 内核若不做这些机制，映射表里也应预留键位（避免将来 460.x 合并时改名）。
